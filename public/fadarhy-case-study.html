Case study  /  FadäRhy  /  2026

Finding the next right connection in the Basel innovation ecosystem.

FadäRhy turns a founder’s few sentences into ranked matches — labs, investors, partners and experts — each with a reason and a source, plus a 12-month plan. I designed the journey, the shared design system and the way we test both.

The challenge

The help exists. The path is unclear.

A founder who needs a BSL-2 lab, regulatory advice or a first grant faces dozens of parks, programmes, funds and institutes across Basel and the Upper Rhine. Finding them is not the hard part; knowing which one fits — and what to do next — is.

01 / INTERPRET

Show what was understood

Founders describe messy situations in plain language. The app must reflect them back and let them correct it.

02 / EXPLAIN

Earn trust with evidence

Every match carries a reason and a source. No unexplained rankings.

03 / ACT

End on a next step

A plan, a shortlist and a draft introduction — not just a list of names.

Step 01 / Map the journey

From a founder’s question to a next step.

The product follows three moves. Each one answers a single question for the founder, so the screen never asks for more than that moment needs.

The model interprets free text and ranks organisations, and both can go wrong. Each pattern below gives the founder a way to see the model’s reasoning or correct it.

TRANSPARENCY

PROVENANCE

Score, reason, source, date

Every card names its source with a verified date. “Why this match” opens the retrieved snippets and an audit reference.

STEERING

HUMAN IN THE LOOP

Intro drafts are editable, and “Open in mail client” stays locked until the founder confirms they’ve read it.

GROUND TRUTH

A directory behind every answer

All 931 organisations stay browsable, so founders can check what the AI left out.

Step 02 / Unify the system

One language. Every interface.

After the hackathon, each designer and developer was working from their own variations. I consolidated them into one component catalog — raw values, semantic roles, components — that now acts as the single source of truth for the app and the landing page.

The October hackathon frontend had 111 hard-coded hex values, its own orange focus colour and two typefaces. The catalog replaces all of that with named roles.

Step 03 / Check the build

Rules that people and AI tools can follow.

Much of the frontend is written with AI assistance. A system only holds if those tools get the same constraints as the team, so the catalog is also written down as instructions.

01

Codify

Component and page conventions live in an instruction file (CLAUDE.md) that points each task to the right token and component spec — so nothing invents a new colour or radius.

02

Lint Proposed

Automated checks should flag hard-coded colours and unknown tokens before review.

03

Review

A person checks what linting can’t: hierarchy, both themes and keyboard focus, against the table below.

Step 04 / Evaluate the advice

A consistent interface is not enough. Can founders trust the route?

UI checks test the build. Product evals test the advice: given a real request, is it understood correctly, is each match justified, and is the next step sensible?

    A first run: medtech in Basel.

    One pass of the first scenario through the live beta. Sources, dates and correction held up. Four things didn’t, and each points to a specific fix.

    Reflection

    Two kinds of quality. One founder journey.

    The catalog makes FadäRhy look and behave the same everywhere. The journey gives that consistency a job. Evals tie them together: the question is not only whether a component follows the rules, but whether the founder using it understands the match and knows what to do next.
