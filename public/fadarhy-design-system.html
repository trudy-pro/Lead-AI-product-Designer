FadäRhy · Design system case study 01 / The challenge

The problem.

AI could build FadäRhy’s screens. But it couldn’t reliably follow the design decisions behind them.

  1. 1

    Missing design context

    Without written rules for FadäRhy’s tokens and components, the agent guessed: a raw #2446F5 here, a Tailwind blue-600 there, Thread Lime on light grey where it can’t be read.

  2. 2

    No memory between sessions

    A correction like “lime only on dark grounds” was gone by the next session, so the same mistakes kept coming back.

  3. 3

    No way to verify the output

    The founder flows worked, but nothing checked that they matched theme.css, the component specs or WCAG contrast.

Setup

The setup

Problem 1: AI doesn’t know the decisions I’ve made

Closed tokens

A fixed set of colour tokens in 2 layers, primitives and semantic. The AI can only use what’s on the list.

Global mapping

A markdown file that says when to use each token.

Spec files

Markdown specs with guidelines for each page template, component and design pattern

Problem 2: AI starts every session from zero

Project instructions and routing

Standing instructions the agent reads at the start of every session. They point it to the global mapping and the right spec files, instead of starting cold.

Problem 3: No way to check if what’s built matches what’s intended

Audit script

Scans the code after each build and flags anything that breaks the rules.

Process

Process

1. Setting up closed tokens

Before cleaning up the tokens, the agent used colors in 3 different ways:

  1. Hardcoded hex values, e.g. #45AB90
  2. Primitive token
  3. Semantic tokens I never defined, e.g. text-status-good, text-status-critical

All of them used everywhere with no clear logic.

To fix this, I defined the color tokens in 2 layers in theme.css, so the agent can only use what’s on the list.

  • Layer 1, primitives. The raw color values: brand, neutral, and the system colours (success, warning, error, info).
  • Layer 2, semantic. Tokens that describe what a color is for, each mapped to a primitive. I reused the shadcn semantic token names, so I wouldn’t break or rework the library. Where shadcn had no name I needed, like success foreground and muted, I defined my own.

Typography follows the Material 3 type scale, from md-display-large down to md-label-small, set in Neue Frutiger. Corners use one 12px radius for buttons, cards and badges, and 8px for chips. Spacing stays on Tailwind’s defaults. What was missing was when to use each one, which the global mapping covers next.

2. Global mapping

With the tokens in place, the agent still didn’t know when to use which one.

I wrote the rules down in a markdown file. It covers color, typography, spacing, radius and shadow, and says what each token is for, so the agent doesn’t have to guess.

The values stay in theme.css, which is the source of truth. The mapping only holds the usage rules.

3. Spec files

Here is an example of a component spec:

Each section has a job:

  • What it is, Use when, Don’t use when: how the agent decides which component fits.
  • Anatomy: the parts of the component, and which ones are optional.
  • Sizes, variants: the versions that exist and when to apply each one. This stops the agent from picking one at random.
  • States: the available states (e.g. hover, disabled, loading, error).
  • Behavior: how it responds to screen size and device behaviour (e.g. keyboard type).
  • Best practices: the rules I’d otherwise correct by hand.
  • Implementation: notes on how it works in code, mostly for the agent.
  • Props: what the agent can pass in, and what is required.

I didn’t write these from scratch. I had Claude read the codebase and draft a first version of each spec from how the component was actually used, then I refined them one by one. It was faster to correct a draft than to start from a blank page.

Since the process repeats, I built a skill that drafts the first cut of a spec. You can download it in the Resources section.

4. Project instructions and routing

Everything above only works if the agent reads it. Without a standing instruction, each session starts cold and it never opens the global mapping or the specs.

So I put the rules in CLAUDE.md, which Claude Code loads at the start of every session. It does 3 jobs:

  1. Routing. It tells the agent which files to read before touching UI: the design system index first, then the spec for any component it is about to use, then the token reference.
  2. Rules against drift. The spec is a constraint, not a suggestion. If a spec doesn’t cover a case, the agent flags the gap and asks.
  3. Audit step. It runs the audit script at the end of the build, and suggests fixes if it catches any drift.

5. Audit script

Rules only help if someone checks them. For FadäRhy that check is a script, scripts/token-audit.js. After every build it reads through the components and pages and looks for three kinds of drift: raw colour values, primitives used where a semantic token belongs, and token names that theme.css never defines.

Every finding comes with the file, the line, what it found and the token to use instead. Because CLAUDE.md makes the audit the last step of each build, drift is caught in the same session that introduced it.

Testing

Testing the setup

These are notes from building the FadäRhy system with Claude, not a controlled experiment. They show where the setup earned its place and where it still slips.

What works

Real sources beat good guesses. In the first attempt the agent could read the site’s copy but not its stylesheet, so it invented a deep teal brand colour. Once it had the brand sheet, every brand value came out exact. That gap is the reason the routing step exists.

The contrast check finds what I would miss. Measuring every pairing in code surfaced two problems I wouldn’t have spotted by eye:

  • A brighter Rhine Blue as small text on its own tint was 4.2:1, just under AA. Going back to the brand sheet’s #2446F5 fixed it: 5.1:1 on the same tint.
  • Thread Lime on Mist was 1.0:1, effectively invisible. That became the rule that lime only sits on dark or blue grounds.

Rendering both themes catches layout bugs. Screenshots of every component in light and dark caught squashed thread nodes and step labels that didn’t sit under their nodes, before anyone saw them.

What doesn’t quite work yet

A written rule is not always a followed rule. The brand book already said lime never sits on Mist, yet the first cover drawing put a lime block straight on it. The render check caught it, not the rule. My guess is the rule needs to be phrased as a hard check, not as guidance.

Starting early created two versions. Because the first draft came before the brand sheet, there were briefly two design systems that had to be merged. That is exactly the kind of drift the setup is meant to prevent.

It costs time. Every change is followed by a contrast run and a render in both themes. It is slower than eyeballing, but each round ends with a list of facts instead of a feeling.

Open questions

What I’m still working out

  1. How do I turn guidance into a check?

    “Lime never on Mist” was written down and still broken once. The rules that held were the ones a script could measure. I want to find out how many brand rules can move from the README into the audit.

  2. Where does Figma fit?

    FadäRhy’s decisions now live in theme.css, the specs and the code. The team still sketches in Figma. Keeping Figma variables in sync with the tokens, and deciding which side wins when they disagree, is the next gap to close.

  3. Who owns the rules on a team of five?

    Right now I update the specs. As more of the team builds with AI, someone has to approve changes to a spec, the same way code changes get reviewed. A pull request per rule change is my first idea.

  4. Can one source serve both readers?

    Agents read markdown and JSON; people prefer a browsable page. The published FadäRhy design system is my answer for now: the same tokens and specs, rendered with live previews. I want to see whether the team actually opens it.

Closing

Closing

Giving the agent a closed list, written rules and a check at the end changed how I work with it. I spend less time repeating corrections and more time deciding what the rules should be.

For FadäRhy the effort pays off because the product is shared: designers, developers and AI assistants all touch the same screens. On a one-person prototype I would keep it lighter, with tokens and an audit first and specs only for the components that keep drifting.

If you build with AI and a design system too, I’d like to compare notes on how you keep the two in step.
